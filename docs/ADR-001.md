# ADR-001: Architecture for Contract Photo → Searchable PDF Web App

**Status:** Accepted  
**Date:** 2026-10-18  
**Author:** TBD  

---

## Context

The user needs a lightweight web application that:
1. Accepts a photo (JPG/PNG) of a physical document (e.g., a labor contract)
2. Converts it into a searchable PDF
3. Allows downloading or forwarding that PDF via email

The primary driver is personal/low-volume usage. Key constraints are:
- **Low infrastructure cost** — no GPU servers or self-hosted ML models
- **Simple deployment** — ideally a single backend service
- **Good OCR accuracy** — must handle real-world photo conditions (slight skew, shadows, varying lighting)
- **Speed** — response within a few seconds per image

---

## Decision

### Technology Choices

| Layer | Choice | Rationale |
|---|---|---|
| **OCR Engine** | Google Cloud Vision API (`DOCUMENT_TEXT_DETECTION`) | Best accuracy for dense document text; REST API; no infra to manage; generous free tier |
| **PDF Generation** | `fpdf2` (Python) or `jsPDF` (browser) | Lightweight, no dependencies, produces standards-compliant PDFs |
| **Backend** | Python (FastAPI) | Clean async support, easy to deploy, excellent Google SDK support |
| **Frontend** | Simple HTML/JS (or Next.js if expanding) | Drag-and-drop upload, preview, download |
| **Hosting** | Google Cloud Run or Railway.app | Serverless, pay-per-request, zero idle cost |

```

```

## PDF Output Strategy

Two layers are embedded in the output PDF:

1. **Image layer** — the original photo rendered at A4/Letter size (preserves visual appearance)
2. **Invisible text layer** — extracted text overlaid at correct positions (makes PDF searchable and copy-pasteable)

This is the same technique used by professional scanning apps (Adobe Scan, Microsoft Lens).

```python
# Pseudocode
from google.cloud import vision
from fpdf import FPDF

def convert(image_bytes: bytes) -> bytes:
    # Step 1: OCR
    client = vision.ImageAnnotatorClient()
    response = client.document_text_detection({"content": image_bytes})
    full_text = response.full_text_annotation.text

    # Step 2: Build PDF
    pdf = FPDF()
    pdf.add_page()
    pdf.image(image_bytes, x=0, y=0, w=210)   # A4 width in mm
    # Optionally overlay invisible text for searchability
    pdf.set_font("Helvetica", size=1)          # size=1 → nearly invisible
    pdf.set_text_color(255, 255, 255)
    pdf.multi_cell(0, 3, full_text)
    return pdf.output()
```

## Considered Alternatives

### Alternative 1: Baidu Unlimited-OCR (self-hosted)

| Factor | Assessment |
|---|---|
| Accuracy | ✅ Excellent |
| Setup | ❌ Requires GPU server (3B param model) |
| Monthly cost | ❌ $50–$200+ (GPU VM) |
| Latency | 🟡 Slow (model inference per request) |
| **Verdict** | ❌ Rejected — severe overkill for this use case |

### Alternative 2: Tesseract (open-source, self-hosted)

| Factor | Assessment |
|---|---|
| Cost | ✅ Free |
| Setup | 🟡 Medium (Python lib, system dep) |
| Accuracy | 🟡 Good for clean scans; degrades on poor lighting/angles |
| **Verdict** | 🟡 Viable fallback if avoiding any cloud dependency |

### Alternative 3: AWS Textract

| Factor | Assessment |
|---|---|
| Accuracy | ✅ Excellent (especially for forms) |
| Cost | $1.50/1,000 pages (no free tier beyond trial) |
| Setup | 🟡 AWS SDK, IAM config overhead |
| **Verdict** | 🟡 Good option but no free tier; GCP Vision is simpler |

### Alternative 4: Client-side only (jsPDF, no backend)

| Factor | Assessment |
|---|---|
| Privacy | ✅ Data never leaves user's device |
| OCR accuracy | ❌ No real OCR — image-in-PDF only (not searchable) |
| **Verdict** | ✅ Use if searchability is not required |

## Consequences

### Positive
- Near-zero cost for personal and small-team use
- No infrastructure to maintain (fully serverless)
- Handles real-world photo quality well (skew, lighting, shadows)
- Output PDF is searchable and email-friendly

### Negative / Trade-offs
- **Privacy:** Images are sent to Google's servers. Not suitable for highly confidential documents if organizational policy prohibits third-party cloud processing.
- **API dependency:** Subject to Google's pricing changes and service availability.
- **Internet required:** No offline mode.

### Mitigations
- For privacy-sensitive deployments: swap Vision API for self-hosted Tesseract with minimal code change
- Add client-side file size validation (e.g., reject images > 5MB) to keep costs and latency low

## Multi-Page Support

Users can upload **multiple images** (e.g., page 1 and page 2 of a contract) and receive a **single merged PDF**.

### Constraints
- Max **10 images** per conversion session
- Max **10MB per image**
- Images are ordered by upload order (user can reorder via drag-and-drop in UI)

### Flow Change

```
User uploads N images (ordered)
  ↓
Backend calls Vision API N times (in parallel via asyncio.gather)
  ↓
Each image → OCR text + bounding boxes
  ↓
PDF generator creates one page per image (image layer + text layer)
  ↓
Single multi-page PDF returned for download
```

### Cost Implication
Each image in a batch = 1 billable unit. A 3-image upload = 3 units.

## Access Control Strategy

### Decision: Public Access + Abuse Prevention Layers (No Login Required)

Requiring login adds friction for a tool meant for quick, easy sharing. Instead, layered server-side guardrails prevent abuse while keeping the experience frictionless for real users.

### Protection Layers

| Layer | Implementation | Purpose |
|---|---|---|
| **IP Rate Limit** | `slowapi` (FastAPI middleware) — 10 requests/IP/day | Prevents bulk scraping |
| **Request Throttle** | 1 request per 5 seconds per IP | Prevents rapid-fire spam |
| **Payload Cap** | Max 10 images, 10MB each per request | Prevents large payload abuse |
| **reCAPTCHA v3** | Google reCAPTCHA v3 (invisible, no user friction) | Bot detection |
| **Timeout** | 30s max processing time per request | Prevents hanging connections |

> [!NOTE] reCAPTCHA v3 is completely invisible to legitimate users — it runs silently in the background and scores each request. No checkbox, no puzzle.

### Rate Limit Response Headers (for transparency)

```
X-RateLimit-Limit: 10
X-RateLimit-Remaining: 7
X-RateLimit-Reset: 1729274400
```

### Upgrade Path (if free tier is ever exhausted)

If usage grows beyond ~330 sessions/day, add **Google Sign-In (OAuth)** as a one-click gate. Low-effort retrofit:
- Frontend: Add a "Sign in with Google" button (one JS call via `@react-oauth/google`)
- Backend: Validate the Google ID token on each request (no user DB needed)
- Per-user rate limit replaces per-IP rate limit
